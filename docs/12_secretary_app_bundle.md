# 秘書アプリ向けデータバンドル

## 目的

秘書アプリは、分析・秘書・通知の3モジュールをすべて端末内で動かす。アプリは Python を実行しないため、このリポジトリが **データだけのバンドル** を書き出し、アプリはそれを同梱して読む。

```bash
python scripts/export_app_bundle.py            # exports/app_bundle/ に2020〜2040年分を出力
python scripts/export_app_bundle.py --start 2026-01-01 --end 2030-12-31 --out <dir>
```

| ファイル | 内容 |
|---|---|
| `manifest.json` | 形式名、ランタイム版、規則版、暦の対象期間、各ファイルの SHA-256 |
| `knowledge.json` | 暦注・九星気学・数秘術・宿曜の公開項目と、分析規則が参照する項目のID |
| `notification_profile_rules.json` | 分析規則（質問、行動シグナル、傾向、軸、プリセット、連続回数ルール） |
| `calendar_2020_2040.json` | 日ごとの旧暦・六曜・日干支・十二直・二十四節気・選日・雑節・九星日盤 |

## 分析規則と参照実装（`analysis_profile`）

`analysis_engine` の読み取り専用ランタイムとは別のパッケージ。アプリはこのロジックを移植し、同じ入力で同じ結果になることを一致テストで確かめる。

- `analyze(answers, behavior)`：質問の回答（1〜5）と行動の集計値（`{"rate", "samples"}`）から、その場限りの傾向（0〜1）を返す。最低件数に満たない行動シグナルは無視する。
- `to_parameters(snapshot)`：傾向を軸①〜⑤（1〜5）へ変換する。
- `derive_parameters(...)`：分析・変換・破棄を一度に行う。アプリはこの形で使う。
- `recommend_presets(axes)`：軸の値に近いタイプを3つ返す（L1距離）。
- `apply_streak_event(state, event, today, target_id)`：反応イベントを数え、5回連続で調整または提案を返す。自動で動かすのは「通知を減らす」「早める」方向だけで、1日1軸1段階、手動設定値から±2段階までとする。

### 傾向を残さない仕組み

- `TendencySnapshot` は `repr` で値を出さず、pickle と JSON 変換を拒否し、`__dict__` を持たない。`discard()` 後は読めない。
- `NotificationParameters.to_dict()` が返すのは `axes`・`fortuneStance`・`rulesVersion` だけ。
- 臨床系ドメイン（`DOM-000009` など）は規則の `knowledge_refs` に現れるが、バンドルの `knowledge.json` には **IDだけ** を入れ、名称や説明文を含めない。利用者に見せる理由文（`reason_ja`）とタイプ名・質問文には、`forbidden_output_terms` の語を使わない（テストで検査）。

## 暦の事前計算（`calendar_tables`）

| 項目 | 方式 |
|---|---|
| 天体計算 | Meeus『Astronomical Algorithms』。太陽は VSOP87 の打ち切り級数、月は ELP-2000/82 の打ち切り（第47章）、ΔT は Espenak-Meeus 式 |
| 旧暦 | `jst_chuki_first_missing_v1`：JST の日付、朔日を月初、中気で月名、冬至を含む月を11月、13か月の年は中気のない最初の月を閏月とする |
| 2033年問題 | 上記規則で閏十一月となる（日本カレンダー暦文化振興協会の推奨と同じ） |
| 九星日盤 | `nearest_kinoe_ne_to_solstice_no_leap_adjustment_v1`：冬至・夏至に最も近い甲子日で陽遁（一白から）・陰遁（九紫から）を切り替える。閏の調整は行わない。同距離の場合は前の甲子日 |
| 社日 | `nearest_tsuchinoe_to_equinox_noon_tiebreak_v1`：春分・秋分に最も近い戊の日。同距離なら、正午より前の分点は前の戊、それ以外は後の戊 |
| 対象期間 | 2020-01-01〜2040-12-31。範囲外は `CalendarRangeError` で失敗させる |

### 検証

- 太陽・月の黄経が Meeus の例題（25.b、47.a）と 1 秒角以内で一致する。
- 同じ規則を UTC+8 で計算すると、2020〜2040年の中国の春節21件と完全に一致する。JST では2027年と2028年だけ1日ずれる。これは、朔が JST の午前0時台に入るための実際の日中差である。
- 閏月（2020年閏4月、2023年閏2月、2025年閏6月、2028年閏5月、2031年閏3月、2033年閏11月、2036年閏6月、2039年閏5月）が既知の値と一致する。
- 旧正月は必ず先勝、六曜は月内で循環、十二直は節入り日だけ重複、選日の出現頻度が規則どおり、などを全日で検査する。
- 公刊の暦（国立天文台の暦要項など）との全日照合は、まだ行っていない。リリース前に、少なくとも2026〜2030年分を照合する。

## 未対応

- 吉方位の判定（本命星と日盤から方位を選ぶ処理）は、まだ含まない。日盤の中宮星だけを出力する。
- 天恩日・母倉日・大明日・神吉日・月徳日・鬼宿日・受死日・十死日・帰忌日・血忌日・往亡日・重日・復日は参照項目のみで、日付表には出していない。算出規則の流派差を確認してから追加する。
